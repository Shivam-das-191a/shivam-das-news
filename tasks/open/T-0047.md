## Goal
`site/public/admin/js/hosting-screen.js` has `hostingScreen({ list | run, onRetry, onConfirm, onReplace?, canEdit? })`: it draws the result list of `hosting-result.js` (headline, notices, one row for each picture, the buttons) and calls the functions it is given. It answers `{ el, update, setBusy }`. It does not fetch, save or read a token.

## Why it matters
The data of the list exists (3c-4) and the pipeline exists (3c-5), but the writer cannot see or press anything. A screen that sends two requests on a double click, shows an address as HTML, or offers Retry for a refused picture would waste downloads or open a hole in the dashboard. Nothing calls it yet, so the live site and the dashboard do not change.

## Steps
1. Read `hosting-result.js`, `hosting-pipeline.js` (`plainMessage`) and `ui.js` (`h`), and one older screen (`bulk-alt.js`) for the style.
2. Write `hosting-screen.js`: `hostingScreen`.
3. Write `site/tests/unit/hosting-screen.test.ts` (jsdom): the headline and notices, the rows, which buttons a row gets, the bar, the calls, one job at a time, what a job answers, `update`, bad input, text never HTML, and a read of the source.
4. Make deliberate mistakes and see the tests fail; close the gaps.
5. Bump the version, write the changelog, update `CODING_PLAN.md`, `INCOMPLETE.md`, `UPDATE_NOTE.md`.

## Done when
- `npm test`, `npm run build` and `npm run preflight` pass; older tests pass unchanged.
- A refused, hosted or reused picture has no button; Retry only where trying again can help; Confirm only for a picture that waits.
- Only one job runs at a time; a job that throws shows one plain sentence with no token and the list stays.
- Every text is a text node; the file has no `innerHTML`, no network, no storage.
