## Goal
The owner opens a picture in Files, chooses a new file of the same kind, and the picture is replaced at the same address in one commit, with the alt text, caption and credit kept.

## Why it matters
A better version of a picture should not need new addresses in every post. The plan (PLAN 33.3) says the address stays the same.

## Steps
1. Read `NEWS_WEBSITE_PLAN.md` 33.3 and 33.5, and `BUGS.md` U13 (the two disagree: see Stop and ask).
2. Add `pictureKind`, `replaceCheck` and `REPLACE_MAX_BYTES` to `media-meta.js`.
3. Add the Replace part to `files-screen.js` (chooser, name and size, red and yellow lines, two steps).
4. Add the right `media:replace` (admin, editor) to `roles.js`; wire `canReplace` and `onReplace` in `app.js` (role check, file check, one commit at the same path, new preview).
5. Write the jsdom tests, make deliberate mistakes, run the whole suite and the build.
6. Bump the version, write the changelog, update `CODING_PLAN.md` and `INCOMPLETE.md` (`VERSIONING.md`).

## Done when
- `npm test`, `npm run build` and `npm run preflight` pass; older tests pass unchanged.
- In a jsdom test: a file of another kind is refused by its bytes and has no Yes button; a good file needs the file choice and one Yes; Cancel sends nothing; Yes calls the replace once and the new size shows; a failed replace changes nothing; a role without the right sees no chooser; `app.js` checks the role and the file again and makes one commit at the same path that deletes nothing.

## Evidence
- Tests: before this change `Test Files 130 passed (130), Tests 2430 passed (2430)`; after it `Test Files 131 passed (131), Tests 2458 passed (2458)`; 28 new tests in `site/tests/unit/admin-file-replace.test.ts`.
