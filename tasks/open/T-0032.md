## Goal
An editor or admin can rename a picture in the Files screen: one name, one question, one commit that moves the picture, updates every file that names it, adds the 301 and moves the alt text.

## Why it matters
PLAN 33.3 says a rename keeps the old address working and updates the posts in the same commit. The rules (T-0031) and the redirect target rule (T-0030) are ready; this part connects them to a screen and to GitHub.

## Steps
1. Read `NEWS_WEBSITE_PLAN.md` 33.3, `public/admin/js/file-rename.js`, `files-screen.js`, the `onDelete` and `onReplace` handlers in `app.js`, `roles.js`.
2. Add `media:rename` to the roles of admin and editor.
3. Add `renameBox` (name, one question, Cancel) and the options `canRename` and `onRename` to the Files screen; update the screen's copies of the post texts after a rename.
4. Add `onRename` to `app.js`: role first, read everything again, `planFileRename`, one `commitFiles` (bytes at the new path, old path deleted, the text files).
5. Write the tests (screen, roles, order of steps, the real `app.js` with a fake GitHub), make deliberate mistakes, run the whole suite and the build.
6. Bump the version, write the changelog, update `CODING_PLAN.md` and `INCOMPLETE.md` (`VERSIONING.md`).

## Done when
- `npm test`, `npm run build` and `npm run preflight` pass; older tests pass unchanged.
- A bad name is refused on the screen and nothing is sent; Cancel sends nothing.
- Yes makes exactly one commit with the bytes at the new path, the old path removed, the changed posts, one 301 and the moved `config/media.json` entry.
- An author cannot rename; the role is checked again inside the save; a missing file or a moved branch changes nothing.
