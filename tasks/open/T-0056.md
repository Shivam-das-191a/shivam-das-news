## Goal
The browser step that makes the smaller WebP copies of one hosted picture (480, 800, 1200, 1600 pixels wide, as planned by `hosting-srcset.js`). It returns the bytes of each copy; it writes no file and sends nothing.

## Why it matters
The next part (4c-3) puts the copies in the ONE commit. It needs the bytes, the width, the height and the path of every copy, all or nothing, so a `srcset` can never name a copy that does not exist.

## Steps
1. Read PLAN 34.5, `hosting-srcset.js` (`variantsFor`) and `hosting-optimize.js` (`optimizePicture`).
2. Add to `hosting-optimize.js`: `isWebpBytes`, `resizeWebp` (the default browser step: decode, draw smaller, encode WebP at 0.85), `makeVariants(main, deps)`, `makeVariantMaker(deps)`.
3. Rules: sizes come only from `variantsFor`; a GIF, JPEG, PNG or a picture of 480 pixels or less gives `[]` and the browser step is not called; the main bytes must be WebP; every answer must be WebP; one failed copy fails the whole call with a plain sentence that names the width.
4. Write `site/tests/unit/hosting-variants.test.ts` (33 tests); relax one line of `hosting-srcset.test.ts` (the file is now imported by `hosting-optimize.js`, and only by it).
5. Make deliberate mistakes and see the tests fail.
6. Bump the version, write the changelog, update `CODING_PLAN.md`, `INCOMPLETE.md`, `UPDATE_NOTE.md`.

## Done when
- `npm test` passes (all older tests unchanged except the one import line named in step 4).
- `makeVariants` of a 2400 x 1200 WebP asks for 480x240, 800x400, 1200x600, 1600x800, in that order, and returns WebP bytes with the paths of `variantsFor`.
- A copy is never as wide as the picture; a picture of 480 pixels or less gets none.
- No page, no screen and no other file calls `makeVariants`, `makeVariantMaker` or `resizeWebp`.
